Resizable

arrow_back arrow_forward

Norbielink has no split panes and no drag handles. Nothing in the product is resized by dragging a divider. The single resize affordance is the browser’s own vertical grip on a textarea, and it is granted deliberately — five fields allow it, ten switch it off.

Resizable textarea

Granted where the answer has no predictable length: free-form descriptions on an endorsement request. The field starts at three rows and can only grow down.

Fixed textarea

Denied where the field sits in a fixed-height panel or a dialog, because growing it would push the surrounding layout. These use resize: none and a row count instead.

Where each is used

SurfaceResizeWhy
Endorsement request — operations, exposure change, additional commentverticalFree-form answer, no predictable length, and the page already scrolls
Add Activity dialognoneFixed-height dialog; growing the field would push the footer buttons
Notes editornoneFills its pane with rows 12–22; the pane is the scroll container
Operations description on a quotenoneSized to the card with height: calc(100% - 22px)
The rule is positional, not aesthetic: resize is allowed when the field’s container scrolls, and denied when it does not. A field in a fixed-height dialog or pane is always resize: none.
The grip is the browser’s, not a drawn control — there is no custom handle, and it renders differently per platform. Nothing in the product styles or replaces it.
Panels that change size do so in two fixed states, not by dragging: a detail panel expands to 70vw and collapses back. That is a sheet, not a resizable pane.
See Textarea for the field itself; this page only covers the resize decision.
